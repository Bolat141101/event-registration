# Граница outbox и дальнейшее масштабирование worker

Сейчас реализованы транзакционная постановка/актуализация outbox, фиксация JSON v1 под event-lock и последовательный async HTTP relay с устойчивыми к перезапуску повторами/backoff. Notifications идемпотентно сохраняет задания до 202. SMTP и сохранение MIME остаются следующим этапом; forwarded не означает sent. [Протокол и гарантии](NOTIFICATION_PROTOCOL.md).

## Текущий контракт

- Бизнес-сервисы регистрации/отказа/переноса изменяют состояние и добавляют outbox в одну переданную SQLAlchemy AsyncSession, в одной async-транзакции. Они не запускают worker и не вызывают SMTP.
- Модуль `notifications` внутри Core отвечает за dedup_key и контекст уведомления. Relay передаёт подготовленный payload, отдельный Notifications будет отвечать за MIME и SMTP. Это обычные функции, без универсальной очереди и лишних интерфейсов.
- Сейчас работает один relay; будущий sender также будет последовательным. Core prepared_at фиксирует неизменность payload, Notifications отдельно сохраняет MIME; это не владение задачей. Message-ID определяется outbox.id, бизнес-дедупликация — UNIQUE(dedup_key).
- FIFO-продвижение выполняется бизнес-транзакцией под блокировкой events и не зависит от доступности отправителя.
- Одна реплика worker; старый процесс должен полностью завершиться до старта нового. Не масштабировать текущий процесс командой `--scale worker=2`.

API и проверка БД worker используют asyncpg; ожидание интервала/остановки — asyncio.Event с timeout. Следующая реализация отправки также должна освобождать AsyncSession до SMTP. При будущем параллелизме каждая задача получает собственную AsyncSession; совместное использование одной сессии несколькими задачами запрещено. Асинхронный доступ сам по себе не создаёт распределённого владения outbox.

## Уточнение Core + Notifications

Согласована граница: Core фиксирует неизменяемый payload, Notifications формирует и сохраняет MIME. Сейчас Notifications имеет таблицу/миграции, health и защищённый идемпотентный приём, без SMTP. Подробности — [NOTIFICATIONS_INFRASTRUCTURE.md](NOTIFICATIONS_INFRASTRUCTURE.md). Core worker теперь выполняет роль relay.

В следующем этапе Notifications получит один последовательный sender. Каждый процесс работает только со своей БД и обычной ролью. Сеть и SMTP не выполняются внутри транзакций Core. После фиксации MIME повтор должен использовать прежние байты; nullable mime в текущей схеме лишь оставляет место под это правило, не реализует его.

## Переход к конкурентной обработке — только после измерений

1. Для нескольких Core relay понадобится следующая миграция Core outbox: отдельные lease_token/locked_until и индекс. Готовые строки выбираются короткой транзакцией FOR UPDATE SKIP LOCKED, владелец фиксируется до HTTP-вызова. Предварительная проверка/заморозка payload сохраняет порядок event → outbox, без удержания outbox-lock при ожидании события.
2. Для нескольких Notifications sender аналогичная независимая миграция нужна в его БД: claim, lease, повтор после истечения срока, завершение только с актуальным токеном. Core не участвует в аренде Notifications-задач.
3. SKIP LOCKED применим к независимым заданиям, но не к FIFO-участникам. Регистрация/отмена/продвижение остаются одной Core-транзакцией под event-lock.
4. Истёкший lease не исключает второй внешний HTTP/SMTP-вызов от старого процесса. Поэтому нужны идемпотентный HTTP-приём, прежний ID, неизменный MIME/Message-ID и дедупликация Mailpit. Exactly-once SMTP lease не даёт.
5. Добавить проверки двух процессов каждого типа, падений до/после ACK/SMTP, истечения/продления аренды и устаревшего владельца. У каждой asyncio-задачи собственная AsyncSession.

Алгоритмы выделения мест, FIFO и постановки логических уведомлений не переписываются. Это будущий план, не реализованная инфраструктура. Сейчас нет SMTP sender, leases, Redis, Celery или Kafka; HTTP relay уже реализован.
