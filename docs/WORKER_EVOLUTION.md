# Граница outbox и дальнейшее масштабирование worker

Сейчас реализованы транзакционная постановка/актуализация outbox бизнес-сервисами и инфраструктурный процесс, проверяющий доступность БД. Отправка, повторные попытки и подготовка писем будут реализованы отдельным этапом. Нельзя считать эти гарантии проверенными по одному наличию таблицы.

## Текущий контракт

- Бизнес-сервисы регистрации/отказа/переноса изменяют состояние и добавляют outbox в одну переданную SQLAlchemy AsyncSession, в одной async-транзакции. Они не запускают worker и не вызывают SMTP.
- Модуль `notifications` отвечает за dedup_key и контекст уведомления; подготовка неизменного письма остаётся следующим этапом; worker — за выбор задания и управление попытками; SMTP — за внешнюю отправку. Это обычные функции, без универсальной очереди и лишних интерфейсов.
- В первой версии работает один последовательный отправитель. `prepared_at` фиксирует неизменность письма, а не право владения задачей. `Message-ID` определяется outbox.id, бизнес-дедупликация — UNIQUE(dedup_key).
- FIFO-продвижение выполняется бизнес-транзакцией под блокировкой events и не зависит от доступности отправителя.
- Одна реплика worker; старый процесс должен полностью завершиться до старта нового. Не масштабировать текущий процесс командой `--scale worker=2`.

API и проверка БД worker используют asyncpg; ожидание интервала/остановки — asyncio.Event с timeout. Следующая реализация отправки также должна освобождать AsyncSession до SMTP. При будущем параллелизме каждая задача получает собственную AsyncSession; совместное использование одной сессии несколькими задачами запрещено. Асинхронный доступ сам по себе не создаёт распределённого владения outbox.

## Переход к нескольким отправителям — только после измерений

1. Добавить следующей Alembic-миграцией отдельное состояние владения: `lease_token`, `locked_until` и необходимый индекс. `prepared_at` сохраняет своё назначение.
2. Выбирать готовые outbox-строки короткой транзакцией `FOR UPDATE SKIP LOCKED`, назначать lease и commit. Под SMTP-вызов транзакция открытой не остаётся.
3. `SKIP LOCKED` применим к независимым заданиям уведомлений, но не к FIFO-очереди участников: там пропуск первого нарушит бизнес-правило.
4. Не нарушить общий порядок блокировок. Если нужна проверка события перед первой подготовкой, нельзя держать outbox-lock и ждать event-lock: API берёт event → outbox. Сначала зарезервировать задачу и commit, затем отдельной короткой транзакцией взять event-lock, проверить lease/состояние и подготовить письмо. Либо заранее выбрать event, взять event-lock, затем claim с SKIP LOCKED; это уменьшает параллелизм в одном событии. Выбор подтвердить тестами deadlock и конкуренции.
5. Истёкшие leases возвращаются в обработку; завершение и продление допускаются только с актуальным lease_token. Устаревший отправитель не должен перезаписать состояние нового владельца.
6. Lease не предотвращает два внешних SMTP-вызова, если старый процесс продолжил работу после истечения срока. Поэтому стабильные Message-ID, неизменяемое письмо и идемпотентность получателя остаются обязательны. Ни lease, ни SKIP LOCKED не дают exactly-once SMTP сами по себе.
7. Добавить испытания двух процессов, падения до/после SMTP, истечения/продления lease, устаревшего владельца и переноса события во время подготовки.

Эти изменения касаются схемы outbox, выбора/завершения задач и worker. Алгоритмы выделения мест, FIFO и постановки логических уведомлений не переписываются. Если позднее понадобится Celery, источник задач остаётся в PostgreSQL; брокер подключается через повторяемый relay, как описано в ARCHITECTURE.md §12.

Текущая версия не реализует leases, конкурентную обработку, Redis или Celery.
